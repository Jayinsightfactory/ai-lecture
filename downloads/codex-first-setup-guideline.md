# Codex 최초 설정 가이드: 작업 규칙, 인계 기록, Skill 만들기

MOYI Astra 실습 배포 원고 | 2026-09-09

이 가이드는 처음 Codex를 사용하는 수강생이 자신의 업무에 맞는 설정을 직접 생성하는 방법을 설명한다. 설정 예시는 교육용 권장안이다. 이 문서를 만든 것만으로 현재 PC의 설정이나 프로젝트 규칙이 바뀌지는 않는다.

## 1. 처음에는 무엇을 만들까?

처음에는 프로젝트의 `AGENTS.md`와 `CURRENT_TASK.md` 두 파일로 시작한다. 반복 업무를 실제로 수행해 보고 안정된 절차가 생기면 Skill 한 개를 추가한다. 여러 번 재사용할 결정이 쌓이면 `DECISIONS.md`를 분리한다. 파일 개수는 Codex의 성능 지표가 아니다.

| 종류 | 쉬운 비유 | 담을 내용 | 만드는 시점 |
|---|---|---|---|
| `AGENTS.md` | 업무 기본 수칙 | 이 프로젝트에서 지속해서 지킬 규칙 | 프로젝트 시작 |
| `CURRENT_TASK.md` | 오늘의 인계장 | 현재 목표·완료·미완료·다음 행동 | 첫 작업부터 |
| `DECISIONS.md` | 결정 기록부 | 확정한 기준과 이유 | 결정이 누적될 때 |
| `SKILL.md` | 특정 업무의 작업 설명서 | 언제 쓰고 어떻게 처리·검증하는지 | 반복 절차가 확인된 뒤 |
| `config.toml` | 프로그램 설정 메뉴 | 기본 모델 등 실행 설정 | 기본값 변경이 필요할 때 |

MD는 Markdown이라는 문서 형식이다. `#`은 제목, `-`는 목록을 나타낸다. MD에 “모델은 Astra”라고 적는 것과 실제 모델 설정을 바꾸는 것은 다르다.

`AGENTS.md`는 Codex의 지시 파일이고, `CURRENT_TASK.md`·`DECISIONS.md`는 이 교육에서 제안하는 일반 문서다. 후자의 이름에 자동 기억 기능이 있는 것은 아니다. 시작 요청이나 `AGENTS.md`에서 필요한 때 읽도록 연결한다. [AGENTS.md 공식 설명](https://learn.chatgpt.com/docs/agent-configuration/agents-md)

## 2. 최초 생성 순서: 30분 준비 실습

| 시간 | 할 일 | 완료 확인 |
|---|---|---|
| 0~5분 | 내 업무·샘플·완료 기준 적기 | 한 업무로 범위가 좁혀짐 |
| 5~15분 | 기존 규칙을 확인하고 MD 두 개 생성 | 내 업무와 실제 파일 위치가 반영됨 |
| 15~25분 | 작은 샘플로 작업 한 번 수행 | 결과와 검증 근거가 남음 |
| 25~30분 | 인계 기록 갱신·새 작업에서 읽기 | 진행 상태를 다시 설명하지 않고 재개 가능 |

Skill 제작은 첫 실행이 성공한 뒤 별도 20분 실습으로 진행한다. 기존에 검증된 반복 절차가 있는 참여자는 바로 Skill 생성부터 시작해도 된다.

### Codex에 처음 붙여 넣는 생성 요청

```text
이 프로젝트에서 반복 설명과 재작업을 줄일 최초 설정을 만들어줘.

내 업무: [예: 주간 주문 CSV를 검토용 Excel로 정리]
사용자: [예: 영업 담당자 2명]
입력 자료: [샘플 경로 또는 파일명]
원하는 결과물: [양식·파일 형식·저장 위치]
업무 규칙: [계산 기준·중복 기준·예외 처리]
완료 기준: [직접 확인할 수 있는 조건]

먼저 현재 프로젝트의 기존 AGENTS.md, 관련 안내 문서,
폴더 구조와 실행·검증 방법을 확인해줘.
관련 없는 대형 파일이나 개인정보 원문까지 읽지는 마.

다음 파일을 내 업무에 맞게 생성하거나 필요한 부분만 갱신해줘.
1. AGENTS.md: 계속 적용할 업무 규칙·결과 위치·검증 기준.
2. CURRENT_TASK.md: 이번 목표·입력·결과·진행 상태·다음 행동.

기존 규칙과 사용자의 수정 내용은 보존하고 중복은 합쳐줘.
확인하지 못한 명령이나 업무 기준을 추정해 사실처럼 적지 마.
사소한 문구·정렬은 판단해서 진행하고,
결과를 바꾸는 정보가 부족하면 핵심 질문만 해줘.
현재 지시 파일 때문에 진행이 막히면 파일과 해당 문구를 알려줘.

이번 범위는 위 문서 설정이다.
모델·권한·연결 도구 설정 변경이나 서비스 배포는 포함하지 않는다.
끝나면 생성 경로, 핵심 규칙, 기존 내용과 달라진 점을 알려줘.
```

`/init`은 `AGENTS.md` 초안을 만드는 출발점으로 사용할 수 있다. 기존 프로젝트에서는 생성된 일반 지침이 실제 규칙과 맞는지 확인하고, 이미 있는 내용을 통째로 교체하지 않게 한다. [Codex 명령 안내](https://learn.chatgpt.com/docs/reference/slash-commands)

## 3. AGENTS.md: 언제나 필요한 규칙만 짧게

아래는 가상의 CSV 실습 프로젝트용 예시다. 자신의 실제 업무와 다른 규칙은 바꾸고 사용한다. 일반적인 앱 개발 프로젝트나 운영 ERP에 그대로 복사하는 공통 규정이 아니다.

```markdown
# 프로젝트 작업 규칙

## 목적
교육용 주문 CSV를 검토 가능한 결과 파일로 변환한다.

## 자료와 결과
- 입력 샘플은 samples/에서 확인한다.
- 입력 원본을 보존하고 결과는 output/에 새 파일로 저장한다.
- 현재 작업을 이어갈 때 CURRENT_TASK.md를 읽고 실제 파일 상태와 대조한다.

## 처리 기준
- 누락·형식 오류·중복 후보를 식별하고 원본 행을 추적 가능하게 남긴다.
- 계산 기준이나 중복 기준이 없으면 결과를 만들기 전에 해당 기준을 확인한다.
- 확인된 규칙으로 처리한 행과 사람의 검토가 필요한 행을 구분한다.

## 진행 방식
- 되돌릴 수 있는 세부 구현은 판단해서 진행하고 중요한 가정을 알려준다.
- 검증은 변경한 동작과 관련 예외에 맞춰 수행한다.
- 필요한 검증을 통과했으면 새로운 문제 없이 같은 검사를 반복하지 않는다.
- 결과를 바꾸는 정보가 부족할 때만 핵심 질문을 한다.

## 완료 보고와 인계
- 결과 파일을 다시 열어 건수·합계·예외 처리 결과를 확인한다.
- 완료한 것, 검증한 것, 확인하지 못한 것을 구분해 보고한다.
- 작업 종료나 인계 시 CURRENT_TASK.md에 상태와 다음 행동을 갱신한다.
```

길이의 공식 정답은 없다. 교육에서는 한 화면에서 읽을 수 있는 초안으로 시작하고, 실제 판단을 바꾸는 규칙만 추가한다. “항상 최고 성능”, “무조건 모든 테스트”, “모든 파일 읽기”처럼 범위가 넓은 지시는 구체적인 조건으로 바꾼다.

### 개인 공통 규칙과 프로젝트 규칙의 위치

- 모든 프로젝트에 적용할 개인 기본 지침: 기본 Codex 홈의 `~/.codex/AGENTS.md`.
- 해당 프로젝트에 적용할 지침: 프로젝트 루트의 `AGENTS.md`.
- 특정 하위 영역만의 지침: 그 영역의 하위 `AGENTS.md`.

기본 경로를 바꾸는 `CODEX_HOME`을 사용하는 환경에서는 실제 Codex 홈을 확인한다. Windows에서 `~`는 사용자 홈을 뜻한다. 개인 공통 지침에는 응답 언어처럼 범용적인 선호만 두고, 특정 회사의 주문 규칙이나 테스트 명령은 프로젝트에 둔다.

Codex는 지시 파일을 계층적으로 읽으며 현재 작업 위치에 가까운 지침이 앞선 지침을 보완하거나 덮어쓸 수 있다. 같은 디렉터리의 `AGENTS.override.md`는 일반 `AGENTS.md`보다 먼저 선택된다. 파일이 많아질수록 중복·충돌을 먼저 확인한다. 지시 문서가 시스템 정책이나 실제 실행 권한을 바꾸는 것은 아니다. [지시 파일 적용 방식](https://learn.chatgpt.com/docs/agent-configuration/agents-md)

## 4. CURRENT_TASK.md: 긴 대화를 다시 읽는 비용 줄이기

대화 전체를 복사하지 말고 지금 이어서 실행할 수 있는 사실을 남긴다. 아래 빈 양식의 ‘미확인’은 실제 확인 후에만 바꾼다.

```markdown
# 현재 작업

- 갱신 시각:
- 목표:
- 완료 기준:

## 입력과 결과
- 입력 파일:
- 결과 파일:

## 확정한 기준
-

## 완료한 작업
-

## 검증 근거
- 확인한 입력과 기대 결과:
- 실제 결과:
- 실행한 검사와 성공·실패:

## 미완료·미확인
-

## 다음 행동
1.
```

이 파일은 자동으로 갱신되지 않는다. 작업 종료나 큰 전환 시 갱신하도록 요청한다. 생성·검증·배포를 하나의 ‘완료’로 묶지 않고 실제 확인한 단계를 적는다. 비밀번호·인증 토큰·개인정보 원문은 인계장에 넣지 않는다.

새 작업에서 사용하는 문장:

```text
AGENTS.md와 CURRENT_TASK.md를 읽어줘.
필요한 결과 파일을 확인해 기록과 실제 상태가 일치하는지 점검한 뒤,
다음 행동부터 이어가줘. 현재 작업과 관련 없는 과거 문서는 읽지 않아도 돼.
```

`/compact` 전에 이 기록을 갱신하면 중요한 결정의 누락을 확인하기 쉽다. 새 작업으로 넘어갈 때도 결과 파일과 함께 인계한다. 압축과 문서 기록은 서로 다른 역할을 한다.

## 5. DECISIONS.md: 같은 결정을 반복하지 않기

한 번 정하고 계속 사용할 판단이 생길 때만 분리한다. 작은 실습은 CURRENT_TASK.md의 ‘확정한 기준’만으로도 충분하다.

```markdown
# 결정 기록

## 2026-09-09 · 중복 후보 처리
- 결정: 주문번호와 품목이 같은 행을 중복 후보로 표시한다.
- 이유: 실제 추가 주문일 수 있어 자동 삭제하지 않는다.
- 적용 범위: 교육용 주문 정리 실습.
- 변경 조건: 실제 업무 식별키와 승인된 처리 기준이 확정되면 재검토한다.
```

이 예시는 특정 프로젝트의 결정 기록이며 모든 주문 시스템에 적용하는 규칙이 아니다. 규칙을 바꿀 때는 날짜·이유·대체 기준을 함께 남긴다.

## 6. 첫 Skill을 만드는 방법

Skill은 매번 쓰는 긴 요청을 ‘업무 이름으로 다시 부를 수 있는 절차’로 정리한 것이다. 예를 들어 보고서 검토 기준이 매번 같다면 이를 Skill로 만든다. 일회성 조사나 아직 기준이 정해지지 않은 업무는 보통 일반 요청으로 시작하는 편이 낫다.

공식 구조는 폴더 안의 `SKILL.md`와 필요에 따른 참고 자료·스크립트·양식이다. `SKILL.md`에는 `name`과 `description`이 필요하다. Codex는 먼저 이름·설명을 보고, 해당 업무에 필요할 때 전체 지침을 읽는다. 이 때문에 ‘언제 사용하는지’가 명확해야 한다. [Skill 제작 공식 설명](https://learn.chatgpt.com/docs/build-skills)

### 생성에 필요한 재료

1. 실제로 성공한 요청 한 개.
2. 그 요청에 사용한 작은 입력 샘플.
3. 좋은 결과의 예시와 확인 기준.
4. 잘못 처리했던 예외와 원하는 처리 방식.
5. 이 Skill이 맡을 범위와 다른 작업과의 경계.

### Skill 생성 요청

```text
$skill-creator

방금 수행한 회의록 실행 항목 정리 업무를 재사용 가능한 Skill로 만들어줘.
이 프로젝트에서만 쓰도록 .agents/skills/meeting-actions/에 생성해줘.

사용할 때: 사용자가 회의 기록을 담당자·기한·실행 항목 표로 정리할 때.
입력: 사용자가 제공한 회의록 또는 텍스트 파일.
결과: 실행 항목, 담당자, 기한, 근거, 미확인 사항을 담은 표.
핵심 규칙: 기록에 없는 담당자나 기한은 만들어내지 않는다.
제외 범위: 이메일 발송, 일정 등록, 프로젝트 관리 도구의 상태 변경.

기존 Skill에 같은 기능이 있는지 먼저 확인해 중복 생성을 피하고,
필요한 경우 기존 Skill의 범위를 보존하며 보완해줘.
SKILL.md에는 name, description과 이 업무에 필요한 절차만 적어줘.
처음에는 설명 중심으로 만들고, 필요 없는 하위 폴더는 만들지 마.
긴 예시가 필요하면 references/로 분리하고 언제 읽는지 연결해줘.
샘플에서 담당자 누락·기한 모호함·실행 항목 없는 경우를 확인해줘.
끝나면 실제 생성 위치와 호출 방법, 검증 결과를 알려줘.
```

`$skill-creator`가 선택되지 않는 환경에서는 “이 내용을 SKILL.md 형식으로 만들어줘”라고 요청하고, 해당 환경의 Skill 메뉴와 인식 경로를 확인한다.

### 최소 SKILL.md 예시

아래 내용은 `meeting-actions/SKILL.md` 한 파일에 들어가는 교육용 예시다.

```markdown
---
name: meeting-actions
description: 제공된 회의 기록에서 실행 항목, 담당자, 기한과 근거를 추출한다. 회의록을 후속 업무 표로 정리할 때 사용한다. 메시지 발송이나 일정 등록은 포함하지 않는다.
---

# 회의록 실행 항목 정리

## 처리
- 사용자가 제공한 회의 기록을 확인한다.
- 확정된 실행 항목과 단순 제안·논의 내용을 구분한다.
- 담당자·기한이 기록에 없으면 미정으로 표시한다.
- 상대 날짜를 변환할 때 기준일이 없으면 원문과 미확인 상태를 남긴다.
- 실행 항목마다 근거가 되는 짧은 문구나 위치를 남긴다.

## 출력
실행 항목 | 담당자 | 기한 | 근거 | 확인 필요

실행 항목이 없으면 없다고 명시한다.
사용자가 다른 출력 형식을 명시했다면 그 형식을 따른다.

## 검증
- 담당자·기한·결정이 원문에 근거하는지 확인한다.
- 같은 실행 항목이 중복되지 않았는지 확인한다.
- 확정되지 않은 논의를 확정 업무로 바꾸지 않았는지 확인한다.
```

### 저장 위치와 호출 확인

프로젝트용 Skill은 `.agents/skills/meeting-actions/SKILL.md`에 둔다. 현재 공식 문서의 사용자 공통 Skill 위치는 `~/.agents/skills`다. 이 작업 환경의 기존 개인 스킬 목록은 `~/.codex/skills`에서도 제공되고 있으므로, 전역 설치는 환경이 실제로 사용하는 경로를 확인한다. 경로가 다르다고 기존 스킬을 임의로 이동하거나 복제하지 않는다. [Skill 탐색 위치](https://learn.chatgpt.com/docs/build-skills)

생성 후 Skill 선택 목록에서 이름을 확인한다. Codex에서 명시적으로 호출할 때는 `$meeting-actions`를 사용한다. 반영되지 않으면 경로·파일명·메타데이터를 확인하고 필요 시 Codex를 다시 시작한다. 특정 업무 요청에서 자동 선택되는지도 별도로 확인한다. 수강생이 쓰는 화면의 Skill 선택 방식이 다르면 해당 메뉴를 따른다.

### 작동 검증: 문법보다 결과

| 실습 입력 | 기대 결과 |
|---|---|
| “민수가 9월 15일까지 초안을 공유하기로 결정했다.” | 담당자·날짜·실행 내용이 근거와 함께 나옴 |
| “다음 주에 자료를 정리하면 좋겠다.” | 확정 여부·담당자·기한의 불확실성을 남김 |
| “지난주 행사 후기를 나눴다.” | 실행 항목을 지어내지 않음 |
| “CSV 합계를 계산해줘.” | 회의록 Skill의 범위 밖으로 구분 |

형식 검사 도구를 제공하는 Skill Creator를 사용한다면 검사도 실행한다. 형식 검사 통과와 실제 업무 결과가 올바른지는 별도로 확인한다. 시험 결과가 없으면 ‘검증 완료’라고 적지 않는다.

## 7. config.toml: 필요한 설정만 바꾸기

초보자는 먼저 앱의 모델·추론 선택 메뉴를 사용한다. 기본 모델을 지속적으로 지정해야 하는 CLI·IDE 사용자는 `config.toml`을 검토한다. 사용자 기본 설정은 일반적으로 `~/.codex/config.toml`, 프로젝트 설정은 `.codex/config.toml`에 둔다. 프로젝트 설정은 신뢰된 프로젝트에서 적용된다. 실행 시 옵션이나 다른 계층의 설정이 최종값을 바꿀 수 있다. [Codex 설정 공식 설명](https://learn.chatgpt.com/docs/config-file/config-basic)

교육용 최소 예시:

```toml
model = "gpt-6-astra"
```

이 한 줄은 해당 환경에서 Astra를 사용할 수 있을 때의 예시다. 기존 파일 전체를 이 내용으로 덮어쓰지 않고 해당 키만 확인한다. 모델 사용 권한이나 사용량을 새로 부여하지 않는다. 앱에서 현재 선택한 모델과 CLI의 기본 모델이 항상 같다고 가정하지 않는다.

| 항목 | 교육용 시작 기준 | 조정할 때 |
|---|---|---|
| 모델 | Astra를 선택할 수 있는 환경에서 Astra | 수강 환경·작업 목적이 달라질 때 |
| 추론 강도 | 일반 실습은 기본값 또는 medium부터 비교 | 규칙 충돌·복잡한 원인 분석에서 상향 |
| Fast | 기본 처리로 실습 시작 | 실제 대기 시간과 사용량을 비교할 때 |
| 권한·승인 | 현재 환경의 허용 범위 유지 | 필요한 작업과 대상이 구체화됐을 때 |
| 하위 에이전트 | 작은 단일 과제는 한 작업에서 수행 | 독립적으로 나눌 일이 있고 실제 이득이 있을 때 |

위 권장값은 강의 운영안이며 모든 환경의 공식 기본값이라는 뜻은 아니다. 응답을 짧게 설정하는 것만으로 추론 비용이나 전체 사용량이 일정 비율 줄어든다고 설명하지 않는다. 반복 확인과 재작업을 실제로 줄였는지 측정한다.

설정을 Codex에 맡길 때 사용할 요청:

```text
현재 환경에서 기본 모델을 Astra로 지정하는 방법을 확인해줘.
민감값을 출력하지 말고 모델 관련 설정과 적용 위치만 확인해줘.
중복 설정·상위 설정 때문에 무시될 가능성도 확인해줘.
변경이 필요하면 기존 설정을 보존하며 model 항목만 변경해줘.
권한·승인·네트워크·연결 도구 설정은 이번 범위에 포함하지 않는다.
끝나면 새 작업에서 실제 선택 모델을 확인하는 방법을 알려줘.
```

## 8. 사용 효율을 떨어뜨리는 설정을 고치는 법

| 비효율적인 지시 | 개선 방향 |
|---|---|
| 매번 모든 MD를 읽어라 | 시작할 때는 현재 상태, 해당 작업에서는 관련 문서만 읽기 |
| 작은 변경에도 전체 테스트를 반복해라 | 변경 동작·영향 범위의 필수 검증 후 종료 |
| 모든 일에 최대 추론을 써라 | 복잡한 설계·판단이 필요한 단계에서만 높여 비교 |
| 무조건 여러 에이전트를 불러라 | 입력·범위가 준비된 독립 작업만 분담 |
| 모든 단계에서 허락을 받아라 | 이미 맡긴 범위의 되돌릴 수 있는 세부사항은 진행 |
| 아무것도 묻지 말고 전부 처리해라 | 결과를 크게 바꾸는 불확실성은 짧게 확인 |
| 실패할 때마다 장문의 규칙 추가 | 원인을 확인하고 해당 업무의 규칙 한 곳만 수정 |
| 동일 절차를 모든 파일에 복사 | 공통 규칙·현재 상태·업무별 절차를 각 한 곳에 관리 |
| ‘회사 업무 전부’를 하나의 Skill로 만들기 | 입력과 결과가 명확한 업무 단위로 분리 |

실제 지침이 서로 충돌하면 Codex에 “충돌하는 파일·문구·영향을 먼저 보여주고 정리해줘”라고 요청한다. 고유한 업무 제약을 ‘짧게 만들기’라는 이유로 삭제하지 않는다.

## 9. 최초 설정 완료 확인

1. 새 작업에서 적용한 지시 파일과 핵심 규칙을 설명하게 한다.
2. 작은 샘플로 결과물을 만들고 요구한 결과 위치·검증 기준을 지켰는지 본다.
3. 생성한 Skill이 해당 업무에서 선택되고 다른 업무를 방해하지 않는지 본다.
4. CURRENT_TASK.md를 갱신한 뒤 새 작업에서 미완료부터 재개해 본다.
5. 불필요한 질문, 반복 읽기, 재작업이 줄었는지 기록한다.

실습 중 남길 측정표:

| 작업 | 기존 소요 시간 | 설정 후 소요 시간 | 반복 설명 횟수 | 재작업 횟수 | 검증 누락 |
|---|---|---|---|---|---|
| 동일 난도의 샘플 업무 | 직접 측정 | 직접 측정 | 직접 기록 | 직접 기록 | 직접 확인 |

효율은 빠른 첫 답변보다 올바른 결과까지 걸리는 전체 시간으로 판단한다. 설정 작성과 유지 시간도 함께 계산한다.

## 10. 강사가 사용할 마무리 설명

“AGENTS.md에는 계속 지킬 원칙을, CURRENT_TASK.md에는 지금 어디까지 했는지를, Skill에는 반복해서 수행할 방법을 적습니다. 처음부터 완벽한 규칙집을 만들 필요는 없습니다. 작은 업무를 한 번 끝내고, 다음에도 유용한 기준만 남겨 보세요.”
