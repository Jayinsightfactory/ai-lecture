⚠️ 사용자의 질문에 답변한다는 개념이 없고, 단순히 입력된 문장에 이어지는 글을 작성합니다.

② 지도 미세조정(SFT) 후
🧑‍🏫 사람이 작성한 좋은 질문과 답변 예시를 학습하여 모방하는 단계

🤖 "안녕하세요. 저는 AI 언어 모델이므로 감정을 가지고 있지 않습니다. 도움이 필요하시면 알려주세요."

✓ 답변하는 형식은 갖췄지만, 어투가 딱딱하고 사무적입니다.

③ 인간 피드백(RLHF) 후
👍 사람이 긍정적으로 평가한 답변 스타일을 학습하여 강화하는 단계

🤖 "고마워요, 그렇게 물어봐 주셔서 😊 저는 감정은 없지만 오늘도 도움이 될 준비는 됐어요! 본인 기분은 어떠세요?"

⭐ 말투가 자연스럽고 친절해지며, 사용자에게 되묻기도 합니다. 우리가 현재 사용하는 AI 모델들은 대부분 이 3단계까지 학습을 마친 상태입니다.

필요한 이유: 오류가 발생했을 때 과거 상황을 재현하고 정확한 원인을 추적하기 위해 필수적입니다.

🕐
히스토리

시스템의 데이터나 파일 상태가 어떻게 변해왔는지 시간 순서대로 차곡차곡 쌓아둔 버전 기록입니다.

필요한 이유: AI가 특정 상황에서 반복적으로 하는 실수 패턴을 분석하고 모델을 교정하기 위함입니다.

⏪
롤백 지점

데이터를 덮어쓰거나 대량 삭제하는 등 위험한 작업을 수행하기 직전에 시스템이 자동으로 남겨두는 백업 지점입니다.

필요한 이유: 대형 사고가 터지더라도 버튼 한 번으로 사고 이전의 안전한 상태로 즉시 되돌리기 위해서입니다.

📊
시각 대시보드

현재 AI 에이전트들이 어떤 작업을 하고 있고 어디까지 진행되었는지 시각적인 그래프나 수치로 보여주는 현황판입니다.

필요한 이유: 관리자가 전체 상황을 직관적으로 파악하고, 이상 징후가 보일 때 즉각적으로 개입하여 작업을 중단시키기 위함입니다.

안전한 화면은 세 가지를 바로 알려 줍니다. AI가 무엇을 했는지, 언제 문제가 시작됐는지, 어디까지 되돌릴 수 있는지가 보여야 합니다.

UI · UX · AX
AI 시대를 맞아 소프트웨어 인터페이스의 패러다임이 UI에서 UX로, 그리고 이제는 AX로 진화하고 있습니다.

📊 왜 지금

리서치 기관의 전망에 따르면, 2026년에는 글로벌 기업용 애플리케이션의 약 40% 이상이 업무용 AI 에이전트를 기본으로 탑재할 것 으로 예상됩니다(2025년 기준 5% 미만). 시스템에 얼마나 훌륭한 AX(에이전트 경험)를 녹여내느냐가 곧 기업 솔루션의 새로운 경쟁력이 될 것입니다.

한 줄 정리: UI·UX가 사람이 쓰기 좋은 환경을 만드는 일이라면, AX는 AI가 자료를 읽고 도구를 안전하게 쓰도록 업무 환경을 정리하는 일입니다.

결론 요약: ① AI의 말은 항상 의심하고 팩트 체크할 것, ② 회사의 기밀 데이터는 절대 통째로 넘기지 말 것, ③ AI 모델의 지식 한계를 명확히 알고 외부 도구로 영리하게 보완할 것, ④ 생성물의 저작권과 회사 규정을 반드시 지킬 것.

## 93. 스키마(Schema)의 개념 — 데이터가 반드시 따라야 하는 깐깐한 '구조적 규칙서' 혹은 '설계도'

심화
스키마 (Schema)
스키마(Schema)의 개념 — 데이터가 반드시 따라야 하는 깐깐한 '구조적 규칙서' 혹은 '설계도'

스키마는 받을 데이터 항목, 각 항목의 형식, 필수 여부를 미리 정한 표입니다. AI의 출력을 이 형식에 맞추면 누락과 형식 오류를 처음부터 줄일 수 있습니다.

Fig 1. Schema 정의
contact_schema = { name : string (필수) // 이름 phone : string (필수) // 010-####-#### amount: number (필수) // ≥ 0 date : string (선택) // YYYY-MM-DD }
Fig 2. 인스턴스 검증 (validate)
✓ 적합
{ name:"김철수", phone:"010-1234-5678", amount:12000 }
✗ 위반
{ name:"김철수", phone:"전화없음", amount:"공짜" } └ 실패 사유: phone 필드에 전화번호 형식이 아닌 텍스트가 들어갔고, amount 필드에 숫자 타입이 아닌 문자열('공짜')이 들어가 스키마 규칙을 심각하게 위반했습니다.
Fig 3. AI에서 스키마의 3가지 역할
📐 출력 강제
"'반드시 이 JSON 스키마 구조로만 대답해'라고 지시하면 → AI가 정해진 형틀에 정확히 들어맞는 깔끔한 구조화 데이터를 출력합니다."
🛡️ 검증 게이트
AI가 스키마에 어긋난 엉터리 형식으로 답변을 내놓으면, 시스템 게이트가 이를 즉시 거부하고 AI에게 에러 메시지를 던져 재작업을 강제합니다. 즉, 불량품은 절대 다음 단계로 넘어가지 못합니다.
🏗️ 구조 재설계
AI가 잦은 실수를 저지른다면 프롬프트를 고칠 게 아니라, 헷갈리기 쉬운 스키마의 구조 자체를 명확하게 재설계하여 실수가 일어날 여지 자체를 없애버려야 합니다.
한 줄 정리: 스키마는 데이터 형식을 정한 계약서입니다. AI·개발자·시스템이 같은 형식으로 주고받게 해 자동화 오류를 줄입니다.
